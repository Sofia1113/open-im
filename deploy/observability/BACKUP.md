# 备份与恢复

> 基线日期：2026-07-30

## 恢复目标

| 指标 | 目标 | 当前能力 | 差距 |
| --- | --- | --- | --- |
| **RPO**（可容忍的数据丢失） | 5 分钟 | **24 小时** | 需要 WAL 归档，见下文 |
| **RTO**（可容忍的恢复时长） | 1 小时 | **未知** | 首次演练的数据量不具代表性，见下文 |

**当前 RPO 是 24 小时，不是 5 分钟。** 每日全量备份意味着最坏情况下丢失近一天的数据。
把这个数字写在这里而不是含糊过去，因为它决定了能不能上真实业务——
一个 IM 系统丢掉一天的消息是不可接受的。补齐路径见[配置 PITR](#配置-pitr)。

## 当前的备份构成

| 用途 | 实现 | 频率 | 保留 | 位置 |
| --- | --- | --- | --- | --- |
| 常规备份 | [`backup-cronjob.yaml`](../k8s/backup-cronjob.yaml) | 每日 02:00 (UTC+8) | 30 天 | 对象存储 |
| 部署前快照 | [`cd.yml`](../../.github/workflows/cd.yml) 的 production job | 每次生产部署 | 30 天 | GitHub artifact |
| PITR | **未配置** | — | — | — |

两者职责不同，不能互相替代：

- **常规备份**是灾难恢复的基础。它与发布节奏无关——这正是它存在的理由。
  CD 里的部署前备份看起来能顶替它，但一周不发版就一周没有备份。
- **部署前快照**只解决一个问题：这次部署的迁移出了问题，要回到部署前那一刻。
  它保留在 CI 侧是有意的，方便回滚时立即取用。

## 配置 PITR

把 RPO 从 24 小时降到分钟级需要连续归档（WAL archiving）。这不是应用侧的改动，
而是 PostgreSQL 实例的配置。托管数据库通常已内置，自建则需要：

```conf
# postgresql.conf
wal_level = replica
archive_mode = on
archive_timeout = 300           # 即使 WAL 未满也每 5 分钟归档一次 —— 这一项直接决定 RPO
archive_command = 'mc cp %p backup/openim-backups/wal/%f'
```

**`archive_timeout` 就是 RPO 的下限**：低流量时段 WAL 段可能几小时都填不满,
不设这个参数的话"连续归档"实际上并不连续。

配好之后恢复流程变为：取最近一次全量备份 → 重放到指定时间点的 WAL。
`restore-drill.sh` 目前只演练全量恢复，PITR 落地后需要补一条演练路径。

**托管数据库的选择**：如果用 RDS / Cloud SQL / 阿里云 RDS，PITR 通常开箱可用，
优先用它而不是自己搭 WAL 归档——自建归档意味着自己负责归档的完整性监控，
而"归档静默失败"是一类很难发现的故障。

## 执行恢复演练

```bash
# 从对象存储取最近一次备份
export S3_ENDPOINT=https://s3.example.com
export S3_BUCKET=openim-backups
export S3_ACCESS_KEY=...
export S3_SECRET_KEY=...
./deploy/scripts/restore-drill.sh

# 或者指定本地文件
./deploy/scripts/restore-drill.sh /path/to/openim-20260730T180000Z.dump
```

演练在本地 Docker 里进行，不接触任何生产资源。脚本会：

1. 校验备份文件大小与可读性
2. 启动一个干净的 PostgreSQL 容器
3. `pg_restore --exit-on-error` 恢复（第一个错误就停，避免产生"部分恢复"还返回成功）
4. 验证一组不变量

### 为什么演练必须验证不变量

`pg_restore` 返回 0 只证明文件能解析，不证明数据可用。以下情况都会"恢复成功"：

- 只备份了 schema、没有数据
- 在事务中途拍摄的不一致快照
- 外键约束未生效时产生的孤立记录

脚本检查的不变量：

| 检查 | 期望 | 为什么重要 |
| --- | --- | --- |
| 表数量 ≥ 15 | — | schema 完整 |
| 版本化迁移记录数 ≥ 1 | — | **缺了它恢复出的库不可用**：Flyway 会当作"有表但无记录"，下次启动尝试重新应用 V1 并失败 |
| 失败的迁移记录 | 0 | 备份取自 schema 不一致的库 |
| 借贷不平衡的交易 | 0 | 复式记账的核心不变量 |
| 账户余额与最新流水不一致 | 0 | 余额没有脱离流水漂移 |
| 孤立流水条目 | 0 | 交易与条目对得上 |
| 孤立消息 | 0 | 消息与会话对得上 |
| 红包计数与领取流水不一致 | 0 | 领取记录与状态一致 |

> 借贷平衡按 `direction` 列（DEBIT/CREDIT）分别求和后比较，**不能**用
> `sum(amount) <> 0` 判断——`wallet_entries.amount` 带 `CHECK (amount > 0)` 约束，
> 方向不是用正负号表示的。写错的话对任何一份正确的备份都会报失败。

账务不变量是重点。这个系统里其他数据错了可以修，账错了必须立刻知道——
所以它不在 SLO 的"多少百分比可接受"框架内，而是一个二元判断。

### 首次演练（2026-07-30）

**结果**：恢复成功，9 项检查全部通过——迁移历史完整（V1–V7）、无失败迁移、
借贷平衡、无孤立记录、账户余额与最新流水一致、账户总额 150000 分、
红包计数与领取流水一致。

**演练本身发现了两个脚本缺陷**，都会让演练在真实使用时失败或误报：

1. **端口冲突**：演练默认端口 55432 与 `e2e` profile 的 postgres 相同，
   e2e 容器运行时演练直接失败（`port is already allocated`）。
   已改为 55433，并在脚本里记录了本仓库的完整端口分配。
2. **迁移历史检查取错了记录**：`ORDER BY installed_rank DESC LIMIT 1` 取到的是
   可重复迁移 `R__demo_seed`，它的 `version` 是 NULL——显示为"Flyway 版本：无"，
   看起来像备份丢了迁移历史，实际是查询漏了 `version IS NOT NULL`。
   顺带把这一项从"展示信息"升级为**断言**：备份不含迁移历史时，
   恢复出的库对 Flyway 来说是"有表但无记录"，下次启动会尝试重新应用 V1
   并立即失败——那样的备份能通过 `pg_restore` 却不能用来重建服务。

**这次演练的局限，必须写清楚**：

- 数据量极小（11 条消息、79 KB）。**RTO 的实测值不具代表性**——
  真实数据量下恢复耗时会显著上升，需要在有代表性数据的副本上重测。
- 备份直接由本地 `pg_dump` 生成，**未经过对象存储的上传与下载**。
  CronJob 的完整链路（上传、生命周期清理、跨账号权限）尚未验证。
- 恢复目标是本地 Docker，**不是一个可接管流量的环境**。
  "恢复出数据库"与"服务恢复可用"之间还差 schema 兼容性确认与流量切换。

### 记录要求

- **恢复耗时**要记，它是 RTO 的实测值。目标 1 小时，如果某次演练花了 45 分钟，
  说明数据量增长已经在逼近上限，该考虑并行恢复（`pg_restore -j`）或缩小恢复范围。
- **不变量**列填"全部通过"或具体失败项。失败必须当作 P1 处理——
  备份不可用是一个已经存在但还没爆发的事故。
- **数据量**用于判断备份是否在正常增长。突然变小通常意味着导出不完整。

## 尚未覆盖

- **PITR 未配置**，RPO 实际为 24 小时（见上文）
- **备份加密未配置**：dump 以明文存在对象存储中。应启用服务端加密（SSE）
  或在上传前用 `age` / `gpg` 加密。含用户凭证哈希与消息正文的备份不该明文存放。
- **跨区域复制未配置**：备份与数据库在同一区域，区域级故障会同时失去两者。
- **备份告警依赖 kube-state-metrics**：`OpenIMBackupJobFailed` 与 `OpenIMBackupMissing`
  已写在 [`prometheus-rules.yaml`](./prometheus-rules.yaml)，但需要集群里部署了
  kube-state-metrics 才会生效。未部署时这两条告警不会报错，只是永远不触发——
  部署监控栈时必须确认这一项。
- **Redis 不备份**：这是有意的——Redis 里只有在线状态、限流计数、事件流，
  全部可从数据库重建或可直接丢弃。事件流丢失会损失未消费的实时事件，
  消息本身在数据库里，客户端重连后按 seq 补拉。
