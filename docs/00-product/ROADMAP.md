# 版本路线图与优先级

## 1. 交付原则

- 先保证消息与账务事实可恢复，再增加交互装饰。
- 首版所有 P0 链路必须有可重复的自动化测试或明确的手工验收脚本。
- 演示实现和生产架构的差异必须显式记录，不以“以后优化”掩盖安全或一致性边界。

## 2. 里程碑

| 里程碑 | 目标 | 核心范围 | 出口条件 |
| --- | --- | --- | --- |
| M0 基线 | 可评审、可启动 | 文档、Monorepo、契约、健康检查 | 新成员按 README 在 15 分钟内启动 |
| M1 演示 MVP | 跑通三条主链路 | 登录、会话、文本消息、小型通话、虚拟红包 | 验收文档中 P0 场景通过 |
| M2 业务可用 | 完整日常交流 | 群管理、附件、撤回、TURN、持久化、通知、审计 | 故障恢复与安全基线通过 |
| M3 生产候选 | 可灰度部署 | SFU、多客户端、离线推送、风控、监控、灾备 | 压测、渗透、隐私与合规评审通过 |

## 3. MVP Backlog

### P0（必须）

- 演示登录与 JWT 会话。
- 会话列表、消息历史和实时文本消息。
- WebSocket 重连、ACK、去重和基础游标同步。
- 单聊/群聊通话房间和 WebRTC 信令。
- 麦克风/摄像头控制及成员列表。
- 虚拟钱包余额、等额/随机红包、并发领取、过期规则。
- 结构化日志、健康检查、统一错误响应。
- 核心服务单元测试与端到端冒烟测试。

### P1（应有）

- 好友和群成员完整管理。
- 图片、文件、消息撤回、已读回执。
- 设备管理、远程退出、会话置顶/免打扰。
- TURN 部署与通话网络质量展示。
- PostgreSQL、Redis、对象存储和可靠任务。
- 红包限额、冻结、审计查询与过期退款任务。

### P2（可后续）

- 消息搜索、引用、表情回应、语音消息。
- Electron、iOS、Android 客户端。
- SFU 大房间、屏幕共享、背景虚化。
- 离线推送、内容审核后台、举报处置。
- 端到端加密和企业组织能力。

## 4. 技术债与升级闸门

以下条件出现时必须升级实现，而不是继续放大演示架构：

- 活跃实例超过 1：内存状态迁移至 PostgreSQL/Redis，WebSocket 使用跨实例事件流（Redis Streams 消费组）。
- 需要公网通话：部署 TURN，并监测 relay 比例与建连失败率。
- 通话超过 6 人或移动弱网占比升高：从 Mesh 切换 SFU。
- 接入真实资金：暂停开放，先完成合规、账务双录、风控、对账和灾备专项。
- 日活达到 1 万或消息量显著增长：进行容量模型、分区策略和全链路压测。

## 5. Definition of Done

一个功能只有同时满足以下条件才视为完成：

- 产品规则、错误分支和权限已明确。
- API/事件契约已更新，客户端和服务端类型一致。
- 核心逻辑包含成功、失败、重试/并发测试。
- 日志不泄露令牌、消息敏感内容或完整账务信息。
- 用户可见的加载、空态、断线和错误状态已实现。
- README/运维说明足够让另一位开发者复现。
